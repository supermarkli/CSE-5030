# Lab 2 零基础背景笔记

## 1. 这次 lab 到底在做什么
这次 lab 的目标不是让你背指令，而是让你把下面这条链路真正连起来：

`C/汇编代码 -> RISC-V 指令 -> 编译/链接 -> 生成 ELF -> 放到 Verilator 里运行 -> 观察 CPU 如何一条条执行`

换句话说，这次 lab 想让你理解两件事：

1. `ISA` 规定了指令“应该做什么”
2. CPU 在仿真时会把这些语义真的执行出来，而且你能从日志里看到

## 2. 先补最核心的背景

### 2.1 什么是 ISA
`ISA` 是 `Instruction Set Architecture`，中文通常叫“指令集架构”。

你可以把它理解成：
- 软件和硬件之间的合同
- 程序员能看到的 CPU 行为规范
- 一套约定：有哪些寄存器、有哪些指令、每条指令怎么解释

这次 lab 用的是 `RISC-V ISA`。

### 2.2 什么是 RISC-V
`RISC-V` 是一种开源指令集架构。它定义了：
- 寄存器长什么样
- `add`、`lw`、`sw`、`beq`、`jal` 这类指令是什么意思
- 函数调用时寄存器怎么用

这次 lab 里，重点不是“RISC-V 的历史”，而是它的程序执行模型。

### 2.3 什么是汇编
汇编就是接近机器指令的人类可读写法。

例如：
- `add a0, a1, a2`：把两个寄存器相加
- `addi a0, a0, 1`：给寄存器加一个立即数
- `lw a0, result`：从内存读取数据
- `sw a0, tohost, t5`：把数据写到内存
- `j write_tohost`：无条件跳转

汇编和高级语言的关系：
- `C` 更抽象，适合写逻辑
- 汇编更接近硬件，适合直接观察 CPU 如何执行

### 2.4 什么是“指令语义”
一条指令的“语义”，就是它到底做了什么。

例如：
- `add x3, x1, x2` 的语义：`x3 = x1 + x2`
- `lw x5, 0(x10)` 的语义：从地址 `x10 + 0` 读取一个字到 `x5`
- `beq x1, x2, label` 的语义：如果 `x1 == x2`，就跳到 `label`

这次 lab 的关键就是：
你不仅要知道语义，还要会从 CPU 日志中看出这个语义确实发生了。

## 4. 什么是“裸机”
`bare-metal`，中文常叫“裸机”，意思是：
- 程序直接跑在硬件上
- 没有操作系统帮你做进程管理、文件系统、系统调用
- 你需要自己处理程序入口、内存布局、退出方式

这次 lab 里的程序就是裸机程序，所以会出现这些现象：
- 入口不是普通 Linux 程序的 `main`，而是 `_start`
- 需要自己写 `link.ld`
- 不能依赖宿主机的系统库行为
- 结束程序不是靠正常 shell 退出，而是通过 `tohost` 之类的机制与仿真环境通信

## 5. 什么是 Verilator
`Verilator` 是一个硬件仿真工具。它会把 Verilog/SystemVerilog 设计转换成可执行仿真器，从而让你在软件里“跑 CPU”。

在这次 lab 里，Verilator 的作用是：
- 运行你编译出来的 `ELF`
- 模拟 Rocket Core 执行指令
- 输出详细日志

所以它不是普通的软件调试器，而是“CPU 级别的执行观察器”。

## 6. 为什么要修改 RocketCore.scala
lab 要你修改 `RocketCore.scala`，本质上是在 CPU 内部额外暴露调试信息。

你加进去的那些监控信号，比如：
- `monitor_imm`
- `monitor_opcode`
- `monitor_funct3`
- `monitor_br_taken`
- `monitor_is_load`
- `monitor_is_store`

它们的作用是把一条指令执行时的重要信息打印出来。

所以这一步不是“改 CPU 功能”，而是“给 CPU 加可观测性”。

## 7. CPU 日志里每个字段是什么意思
lab 里最重要的日志格式大致是：

```text
C0: 610 [1] pc=[...] opcode=[...] funct3=[...] W[...] R[...] R[...] imm=[...] is_ld/st=[0/1] is_br(taken)=[0(0)] inst=[...] DASM(...)
```

你要会读这些字段。

### 7.1 Cycle number
例如 `610`。
表示当前仿真周期数。

可以把它理解成 CPU 时钟走到第几拍了。

### 7.2 PC
`pc` 是 `Program Counter`，程序计数器。

它表示：
- 当前执行的是哪条指令
- 下一条通常从哪里取

如果发生跳转或分支，`pc` 的变化会和顺序执行不同。

### 7.3 opcode
`opcode` 是操作码，决定一条指令属于哪一大类。

例如：
- 算术类
- load/store 类
- branch/jump 类

它是机器码中的关键字段。

### 7.4 funct3
`funct3` 是进一步区分具体指令含义的字段。

因为同一个大类下可能有多种操作，所以 CPU 还要看 `funct3`。

### 7.5 W[...]
`W[...]` 表示写回信息。

你可以这样读：
- 写回目标寄存器是谁
- 写回的值是多少
- 这一拍是否真的发生了寄存器写入

如果最后那个标志是 `1`，说明确实把结果写进寄存器了。

### 7.6 R[...]
`R[...]` 表示源寄存器读取信息。

它告诉你：
- 指令读了哪个寄存器
- 读到的值是多少

一般一条常见整数指令会读两个源寄存器，但也可能只读一个，甚至不读。

### 7.7 imm
`imm` 是 `immediate`，立即数。

立即数就是直接编码在指令里的常数。

例如：
- `addi x1, x1, 4` 里的 `4`
- `lw x5, 8(x10)` 里的 `8`
- `beq x1, x2, label` 里的跳转偏移量

### 7.8 is_ld/st
这个字段表示这条指令是不是 load/store：
- 前一位是 load
- 后一位是 store

所以：
- `[1/0]` 表示 load
- `[0/1]` 表示 store
- `[0/0]` 表示都不是

### 7.9 is_br(taken)
这是看分支/跳转最关键的字段。

含义：
- 外层那个值表示“这条是不是 branch 或 jal”
- 括号里的值表示“这次到底跳没跳”

例如：
- `[1(1)]`：这是跳转/分支，而且跳了
- `[1(0)]`：这是跳转/分支，但条件不成立，没有改控制流
- `[0(0)]`：这不是分支类指令

### 7.10 inst
`inst=[fc0f2023]` 这种就是原始机器码编码。

也就是 CPU 真正看到的二进制指令。

### 7.11 DASM
这是反汇编后的可读形式，例如：
- `sw zero, -64(t5)`
- `auipc t5, 0x1`

它有助于你把机器码和汇编语义对应起来。

## 8. Step 1 里会涉及哪些基础概念

### 8.1 寄存器
RISC-V 通用寄存器是 CPU 内部非常快的小存储单元。

lab 中常见寄存器：
- `a0`：常用于函数参数和返回值
- `t5`：临时寄存器
- `zero`：永远等于 `0`

理解寄存器时要记住：
- 算术逻辑通常先在寄存器里做
- 只有 `load/store` 会直接碰内存

### 8.2 内存与地址
数组放在 `.data` 段里，本质上就是一片连续内存。

如果数组元素是 `.dword`：
- 每个元素通常占 `8` 字节
- 遍历数组时，地址常常按 `8` 递增

### 8.3 load/store 结构
RISC-V 是典型的 `load-store architecture`：
- 算术指令只在寄存器之间操作
- 想处理内存数据，必须先 `load`
- 算完再 `store` 回去

所以数组求和的一般流程是：
1. 计算当前元素地址
2. 从内存 `load` 到寄存器
3. 累加到 sum 寄存器
4. 更新指针
5. 分支判断是否继续循环

### 8.4 循环与分支
循环在汇编里不是高级语法，而是：
- 一个标签
- 若干算术指令
- 一条条件分支或无条件跳转

所以 `for`/`while` 最后都会变成：
- 比较
- branch
- 改 `pc`

### 8.5 ALU 指令
`ALU` 是算术逻辑单元。

普通 `ALU instruction` 指的是类似：
- `add`
- `sub`
- `and`
- `or`
- `sll`

它们的特点是：
- 输入主要来自寄存器
- 输出通常写回寄存器
- 不直接访问内存

### 8.6 ALU-immediate 指令
这类指令也是 ALU 运算，但一个操作数来自立即数。

例如：
- `addi`
- `andi`
- `ori`

日志里这类指令通常更容易看到 `imm=[...]` 字段的意义。

## 9. 为什么最终要分析四类指令
lab 要你在日志里各找一个例子：
- 普通 ALU 指令
- 带立即数的 ALU 指令
- load/store 指令
- branch 指令

原因是这四类几乎覆盖了最基础的程序执行模型：
- 计算
- 常数参与计算
- 内存访问
- 控制流改变

如果你能把这四类都讲明白，说明你已经能把“ISA 语义”和“CPU 实际执行”连起来了。

## 10. Step 2 会补哪些更上层的概念

### 10.1 什么是交叉编译
`cross-compilation`，交叉编译，意思是：
- 你当前机器不是目标机器
- 但你在当前机器上生成目标机器能运行的程序

这次就是：
- 宿主机：你的开发机器，通常是 x86 或 ARM Linux
- 目标机：RISC-V CPU

所以不能用系统默认 `gcc`，因为默认 `gcc` 生成的是宿主机架构程序，不是 RISC-V 程序。

### 10.2 为什么用 `riscv64-unknown-elf-gcc`
这个编译器名字本身就带了目标信息：
- `riscv64`：目标架构是 64 位 RISC-V
- `unknown`：厂商字段，不重要
- `elf`：输出目标文件格式是 ELF，说明面向裸机/嵌入式环境，不是 Linux 用户态程序

所以它的核心作用是：
- 生成 RISC-V 指令
- 使用适合裸机环境的链接方式

### 10.3 什么是 ELF
`ELF` 是可执行文件/目标文件格式。

在这次 lab 里：
- `test.elf` 是汇编程序编译链接后的结果
- `hello.elf` 是 C 程序编译链接后的结果

Verilator 会把这些 ELF 加载进去运行。

### 10.4 什么是链接
编译不等于最终能运行。

链接器会做这些事：
- 决定代码和数据放到内存的哪里
- 解析符号
- 生成最终可执行文件

这就是为什么 Step 1 需要 `link.ld`。

## 11. link.ld 的作用
`link.ld` 是链接脚本，用来规定内存布局。

这份 lab 里的脚本主要做了这些事：
- 程序入口设为 `_start`
- 把 `.text.init` 放到 `0x80000000`
- 对 `.tohost`、`.text`、`.data` 做地址布局和对齐

你可以把它理解成“告诉链接器：程序在内存里怎么摆”。

如果没有这一步：
- 裸机程序的地址布局可能不符合仿真环境预期
- CPU 启动后可能跳不到正确位置

## 12. 为什么会有 `.text`、`.data`、`.bss`
这些是常见段（section）：

- `.text`：代码段，放机器指令
- `.data`：已初始化的全局数据
- `.bss`：未初始化的全局数据
- `.text.init`：启动代码
- `.tohost`：和仿真环境通信的特殊区域

在这次 lab 中：
- 数组和 `result` 放在 `.data`
- `_start` 放在 `.text.init`
- `tohost`/`fromhost` 放在特殊段里

## 13. `tohost` / `fromhost` 是什么
这是仿真环境中常见的一种宿主通信机制。

你可以粗略理解成：
- 程序不是直接退出给 shell 看
- 而是把某个结果写到 `tohost`
- 仿真器观察到这个值后，知道程序想表达什么结果

lab 模板里：
- 先 `lw a0, result`
- 再对 `a0` 做位运算
- 然后写到 `tohost`

因此仿真报出的退出码，实际上是在借用一种通信方式输出程序结果。

## 14. 为什么会出现“FAILED”但其实不一定真错
lab 说明里写了，数组求和程序如果正确，反而可能看到：
- `Assertion failed`
- `exit code = 10`

这不一定表示程序逻辑错了。

原因是：
- 仿真环境通常把 `exit code == 1` 视为某种固定成功模式
- 这次实验为了“打印结果”，故意把结果编码到退出值里
- 所以退出码不是默认预期值，仿真器就会报一个表面上的 `FAILED`

重点是要理解：
- 这里你看的是“结果编码机制”
- 不是普通 Linux 程序的成功/失败语义

## 15. Step 2 里的函数调用为什么重要
`hello.c` 里虽然只有一个很小的函数 `f`，但它足够展示：
- 参数如何传递
- 返回值放在哪里
- 调用前后哪些寄存器需要保存
- 汇编如何实现函数跳转

这就是 `calling convention`，调用约定。

## 16. RISC-V 调用约定入门
你至少要知道下面几类寄存器：

- `a0-a7`：参数寄存器，也常承载返回值
- `ra`：返回地址寄存器
- `sp`：栈指针
- `t0-t6`：临时寄存器，调用者保存
- `s0-s11`：保存寄存器，被调用者保存

### 16.1 调用者保存和被调用者保存
这是 Step 2 的核心。

`caller-saved`：调用者保存
- 如果调用者还想保留某些值，就要在调用前自己存起来
- 常见是 `t` 类寄存器和 `a` 类寄存器

`callee-saved`：被调用者保存
- 如果被调用函数要用这些寄存器，就要自己先保存，返回前恢复
- 常见是 `s` 类寄存器

### 16.2 参数和返回值
RISC-V 常见规则：
- 前几个整型参数放在 `a0-a7`
- 返回值通常放在 `a0`

所以 `f(1, 2)` 一般意味着：
- 调用前把 `1`、`2` 放到参数寄存器
- 跳到 `f`
- `f` 算完后把结果放回 `a0`

### 16.3 跳到函数怎么实现
常见实现方式是：
- `jal`：jump and link
- 或者伪指令 `call`

关键语义是：
- 跳到函数地址
- 同时把返回地址写进 `ra`

函数结束时再通过：
- `ret`
- 或等价形式 `jalr x0, 0(ra)`

回到调用点。

## 17. Step 2 为什么要看反汇编
你写的是 C，但 CPU 不执行 C，CPU 执行的是汇编/机器码。

看 `hello.dump` 的目的是：

这会帮助你把“高级语言函数调用”映射到“底层控制流和寄存器操作”。

## 18. 编译选项为什么是 lab 的重点
lab 最后专门问了编译 flag，因为它们不是随便写的。

你需要建立这个意识：

## 19. 这次 lab 中值得提前认识的常见 flag
下面先给你一个“理解版”，不是逐字符手册。

### 19.1 `-static`
静态链接。

含义：
- 尽量把需要的内容在链接期放进最终程序
- 不依赖运行时动态库

为什么适合这里：
- 裸机环境没有普通操作系统的动态链接器

### 19.2 `-march=rv64imafd`
指定目标指令集。

大致表示：
- `rv64`：64 位 RISC-V
- `i`：基础整数指令集
- `m`：乘除法扩展
- `a`：原子指令扩展
- `f`：单精度浮点
- `d`：双精度浮点

为什么需要：
- 编译器必须知道能生成哪些指令
- 否则可能生成与目标 CPU 不匹配的代码

### 19.3 `-mcmodel=medany`
控制代码和数据地址的寻址模型。

为什么 lab 用它：
- 裸机程序常被放在固定的高地址区域
- 编译器需要用合适方式生成可访问这些地址的代码

### 19.4 `-fvisibility=hidden`
默认隐藏符号可见性。

这对这次 lab 不是最核心概念，但它能减少不必要的外部符号暴露，适合较封闭的裸机场景。

### 19.5 `-nostdlib`
不要链接标准库。

为什么需要：
- 裸机程序没有完整的常规运行时环境
- 你不希望链接器自动拉入宿主机或不匹配的标准库内容

### 19.6 `-nostartfiles`
不要使用标准启动文件。

为什么需要：
- 这次 lab 由你自己提供 `_start`
- 如果还链接系统默认启动代码，会和实验预期冲突

### 19.7 `-T link.ld`
指定链接脚本。

为什么需要：
- 裸机程序的内存布局必须由你明确控制
- 默认链接脚本通常不适合当前仿真环境

### 19.8 `-fno-common`
禁止把未初始化全局变量当成 common symbol 处理。

为什么实验里会出现它：
- 这样链接行为更明确
- 对裸机和底层环境通常更稳妥

### 19.9 `-fno-builtin-printf`
不要把 `printf` 当成编译器内建函数做特殊优化。

为什么实验里要这样写：
- 避免编译器按宿主环境假设去替换或优化 `printf`
- 保持和目标环境提供的实现相匹配

很多初学者会把它们看成两件事，其实它们在讲一条完整链路。

- 调用约定怎么落到寄存器和栈上

`高级语言 -> 汇编 -> 机器码 -> CPU 执行 -> 微观日志`

## 21. 做实验前你至少要会的最小词汇表

- `ISA`：指令集架构，软件和硬件之间的规则
- `RISC-V`：本实验使用的指令集架构
- `assembly`：汇编语言
- `register`：寄存器
- `memory`：内存
- `PC`：当前指令地址
- `immediate`：立即数
- `load/store`：读内存/写内存
- `branch`：条件跳转
- `jal`：跳转并保存返回地址
- `ELF`：可执行文件格式
- `linker`：链接器
- `linker script`：链接脚本
- `bare-metal`：无操作系统的运行环境
- `cross-compilation`：交叉编译
- `calling convention`：调用约定
- `prologue/epilogue`：函数序言/函数结尾
- `caller-saved`：调用者保存寄存器
- `callee-saved`：被调用者保存寄存器
